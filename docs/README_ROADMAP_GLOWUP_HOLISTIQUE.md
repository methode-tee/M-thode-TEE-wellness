# 2. PRIORITÉ N°1 — PASSER DU SEUIL GÉNÉRAL AU REPÈRE PERSONNEL

C’est le chantier principal.

Aujourd’hui, certaines décisions reposent encore sur des seuils généraux ou semi-généraux :
- durée de sommeil
- stress
- récupération
- protéines
- fibres
- variation corporelle
- régularité

La prochaine MAJ doit progressivement apprendre **la zone habituelle de chaque personne**.

## À construire

### 2.1 Baseline personnelle
Créer un repère personnel roulant pour chaque signal pertinent :
- sommeil habituel
- énergie habituelle
- stress habituel
- digestion habituelle
- faim / satiété habituelles
- activité habituelle
- récupération habituelle
- poids / mensurations habituels et tendance
- apports énergétiques observés
- protéines
- fibres
- principaux micronutriments réellement documentés
- horaires de repas
- fréquence / régularité des routines

### 2.2 Fenêtres de référence
Prévoir plusieurs fenêtres :
- **7 jours** : contexte très récent
- **28 jours** : tendance principale
- **90 jours / 3 mois** : évolution plus stable
- éventuellement **long terme agrégé** au-delà

### 2.3 Comparaison à soi-même
Le moteur doit pouvoir dire en interne :
- « inhabituellement bas pour cette personne »
- « dans sa zone habituelle »
- « inhabituellement élevé »
- « tendance en amélioration »
- « tendance en dégradation »
- « données trop irrégulières pour conclure »

Ne pas afficher forcément ces formulations telles quelles à l’utilisatrice ; elles servent au raisonnement.

# 3. PRIORITÉ N°2 — AJOUTER LA DIMENSION TEMPORELLE ENTRE LES SIGNAUX

Aujourd’hui, beaucoup de données sont reliées par journée.  
La prochaine étape est de comprendre **ce qui précède et ce qui suit**.

## Cas à couvrir

### Sommeil → lendemain
Relier :
- nuit précédente
- énergie du matin
- faim / envies
- alimentation du jour
- stress
- activité / récupération
- coucher suivant

### Repas → heures suivantes
Relier :
- contenu du repas
- quantité
- heure
- protéines / fibres / lipides / glucides
- digestion post-repas
- satiété
- énergie
- reflux / aigreurs
- envie sucrée ultérieure

### Activité → récupération
Relier :
- entraînement / marche / activité
- énergie active
- fatigue
- récupération
- sommeil suivant
- faim
- douleurs / inconfort lorsque documentés

### Cycle → plusieurs jours
Relier :
- phase du cycle
- sommeil
- humeur
- stress
- faim
- digestion
- rétention / évolution corporelle
- activité / récupération

### Jeûne / horaires → réponse réelle
Relier :
- horaires des repas
- durée de jeûne observée
- faim
- énergie
- digestion
- sommeil
- adhésion réelle

## Règle importante
Une association temporelle n’est **pas une causalité**.

Le moteur doit employer en interne une logique du type :
- association répétée
- signal cohérent
- signal possible
- historique insuffisant

# 4. PRIORITÉ N°3 — GÉRER LES SIGNAUX CONTRADICTOIRES

Le moteur ne doit pas simplement prendre « la dernière valeur » lorsqu’il existe plusieurs signaux pertinents.

## Exemple
Une personne peut avoir :
- stress déclaré : 8/10
- humeur correcte
- sommeil court
- HRV basse
- alimentation correcte
- récupération basse

Il faut apprendre à reconnaître :
- les signaux concordants ;
- les signaux contradictoires ;
- les sources objectives vs ressenties ;
- les valeurs explicites vs données complémentaires ;
- la répétition ou non du phénomène.

## À développer
Créer une couche interne de **concordance** :
- nombre de signaux allant dans le même sens ;
- importance de chaque signal ;
- récence ;
- fiabilité / complétude ;
- répétition sur plusieurs jours ;
- contexte particulier.

## Sortie attendue
Le moteur doit pouvoir décider :
- conclusion suffisamment solide ;
- hypothèse prudente ;
- besoin d’observer encore ;
- aucune interprétation utile pour l’instant.

---

# 5. PRIORITÉ N°4 — FERMER LA BOUCLE : CONSEIL → APPLICATION → RÉPONSE

Aujourd’hui, le cycle 7 jours réévalue déjà les données.  
La prochaine MAJ doit distinguer :

1. **Le conseil a été proposé**
2. **Le conseil a réellement été appliqué**
3. **Il a été appliqué suffisamment souvent**
4. **Les signaux ont changé ensuite**
5. **La priorité doit être maintenue, ajustée ou abandonnée**

## À construire

### 5.1 État du levier
Pour chaque cycle :
- levier proposé
- date de début
- raison principale
- niveau de confiance initial
- actions attendues
- nombre de jours réellement appliqués
- données avant
- données pendant
- données après

### 5.2 Adhésion réelle
Ne pas confondre :
- avoir ouvert une routine
- avoir réellement complété l’action

Même logique pour :
- protocole
- suivi
- objectif nutritionnel
- routine
- hydratation
- activité
- sommeil

### 5.3 Réévaluation
À J7 ou à la fin du cycle :
- amélioration nette
- amélioration partielle
- aucun changement lisible
- aggravation
- données insuffisantes
- adhésion insuffisante pour conclure

### 5.4 Nouvelle décision
Ensuite :
- conserver le même levier ;
- simplifier le levier ;
- choisir un nouveau levier ;
- revenir à Observer ;
- demander une donnée plus précise.

# 6. PRIORITÉ N°5 — CRÉER UN SCORE DE CONFIANCE PLUS FIN

- nombre de suivis réellement complétés

### Qualité / comparabilité

### Récence
- donnée aujourd’hui
- donnée récente
- donnée ancienne

### Nature
- saisie explicite de l’utilisatrice
- donnée calculée depuis Méthode Tee
- donnée Apple Santé
- donnée subjective
- donnée objective

### Concordance
- plusieurs signaux convergents
- signaux contradictoires
- répétition sur plusieurs jours

## Niveaux possibles
Exemple interne :
- insuffisant
- faible
- modéré
- solide
- très solide

L’interface peut rester plus douce :
- Repères en construction
- Lecture en cours de précision
- Lecture évolutive disponible
- Données suffisamment solides

# 7. SYNCHRONISER LE CYCLE ADAPTATIF 7 JOURS AU COMPTE

## Problème actuel
Le cycle adaptatif 7 jours est mémorisé localement sur l’appareil.

Cela veut dire que :
- changement de téléphone ;
- suppression du stockage local ;
- certaines réinstallations ;

peuvent recommencer le compteur visuel du cycle, même si les données santé / nutrition restent sauvegardées.

## À faire
Créer une persistance serveur légère pour :
- priorité actuelle
- date de début du cycle
- jour courant
- dernier état de réévaluation
- niveau de confiance
- éventuellement résumé compact du point de départ

## Contraintes
- ne pas stocker de gros historiques dupliqués ;
- ne pas augmenter inutilement le cached egress ;
- conserver une structure compacte ;
- réutiliser les agrégats existants lorsque possible.

# 8. AMÉLIORER LA PRÉCISION DES LIENS HOLISTIQUES

Les connexions existent.  
Le but n’est plus d’ajouter des connexions « pour ajouter des connexions », mais de vérifier que chaque lien a un sens.

## Matrice à créer
Pour chaque module, définir :

| Source | Peut nourrir | Ne doit pas nourrir | Type de lien |
|---|---|---|---|
| Sommeil | Vitalité, récupération, faim contextuelle | digestion directement | contexte |
| Stress | Équilibre intérieur, digestion contextuelle, sommeil | protéines | contexte |
| Repas | nutrition, satiété, digestion, reflux | humeur directe sans signal | direct/contextuel |
| Cycle | sommeil, faim, digestion, humeur, récupération | pas automatiquement une anomalie | contexte |
| Routine complétée | régularité, adhésion à un levier | stress physiologique fictif | comportement |
| Notre journée ensemble | régularité | santé physiologique fictive | comportement |

Cette matrice doit devenir une référence technique pour éviter qu’un futur patch relie deux choses simplement parce qu’elles existent toutes les deux.

# 10. PROTOCOLES — MESURER L’EFFET RÉEL

Pour chaque protocole compatible :

## Avant
- état initial
- symptômes / ressentis structurés
- habitudes
- données déjà disponibles

## Pendant
- adhésion
- actions complétées
- évolution des repères
- effets ressentis
- événements perturbateurs

## Après
- évolution par rapport au départ
- ce qui semble avoir aidé
- ce qui n’a pas été suffisamment testé
- prochain levier éventuel

## Micro-feedback de fin
Ajouter une fin de protocole légère :
- note /5
- « qu’est-ce qui t’a le plus aidé ? »
- « qu’est-ce qui t’a manqué / semblé moins utile ? »

Ne pas transformer cela en questionnaire interminable.

# 12. UX — LE MOTEUR DOIT RESTER INVISIBLE

Règle éditoriale permanente :

**La mécanique technique appartient à Méthode Tee, pas à l’utilisatrice.**

Ne plus afficher :
- nom des migrations ;
- Supabase ;
- RPC ;
- « source prioritaire » ;
- « déjà pris en compte » ;
- « même date même Carnet » ;
- listes de modules internes ;
- détails sur la déduplication ;
- raisonnement brut du moteur.

## Ce que l’utilisatrice doit voir
Seulement :
- son repère ;
- la tendance utile ;
- la priorité du moment ;
- une explication courte ;
- l’action proposée ;
- la progression ;
- la réévaluation.

Exemple :
> **Priorité cette semaine : récupération**  
> Ton sommeil et ta récupération sont plus fragiles que d’habitude. Avant de modifier ton alimentation, on stabilise d’abord ce terrain pendant quelques jours.

Pas :
> « Données app prioritaires, HealthKit fallback, RPC contexte… »

---

# 13. GARDE-FOUS À CONSERVER

- Ne jamais transformer une donnée manquante en zéro.
- Ne jamais fabriquer un suivi pour donner l’impression qu’il a été rempli.
- Ne jamais interpréter arbitrairement du texte libre.
- Utiliser uniquement les données structurées lorsqu’un raisonnement automatique est nécessaire.
- Ne jamais déduire une cause certaine à partir d’une corrélation.
- Ne jamais réduire automatiquement les calories parce que le poids ne bouge pas.
- Toujours vérifier récupération, sommeil, protéines, fibres, adhésion et comparabilité avant une décision énergétique.
- Ne jamais faire monter une jauge physiologique grâce à un clic sans signification corporelle.
- Ne jamais écraser une saisie explicite par Apple Santé.
- Pour les pas : Apple Santé peut rester la source passive principale.
- Garder les recommandations prudentes lorsque l’historique est insuffisant.
- Préserver les garde-fous mineurs / profils non éligibles aux calculs énergétiques adultes.

# 14. PERFORMANCE / SUPABASE / EGRESS

La sophistication doit venir du raisonnement, pas d’une explosion des requêtes.

## À conserver
- agrégats compacts ;
- appels mutualisés ;
- cache client raisonnable ;
- pas de duplication d’historique ;
- pas de texte libre téléchargé inutilement ;
- limites temporelles explicites ;
- snapshots versionnés lorsque la formule change.

## À privilégier
- une ou quelques RPC compactes plutôt qu’une requête par tracker ;
- agrégation serveur lorsque cela évite de transférer des centaines de lignes ;
- stockage de résumés de cycle plutôt que duplication des mesures brutes ;
- recalcul uniquement lorsque la donnée source change.

# 19. DÉFINITION DU SUCCÈS DE CETTE MAJ

La prochaine MAJ sera réussie si Méthode Tee peut, avec prudence :

1. reconnaître ce qui est habituel **pour cette personne** ;
2. détecter ce qui change réellement ;
3. relier plusieurs dimensions sans les confondre ;
4. tenir compte du temps entre les événements ;
5. savoir quand les données concordent ou se contredisent ;
6. choisir un seul levier prioritaire ;
7. vérifier si ce levier a réellement été appliqué ;
8. mesurer si les repères ont évolué ensuite ;
9. réévaluer sans surinterpréter ;
10. montrer à l’utilisatrice une conclusion simple et utile, sans exposer toute la mécanique.

---

## Phrase directrice

**Méthode Tee ne doit pas simplement compter ce que la personne fait.  
Elle doit apprendre à lire comment son ensemble évolue, puis l’aider à ajuster une chose juste au bon moment.**
